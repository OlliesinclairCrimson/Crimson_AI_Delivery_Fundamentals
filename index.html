Six fundamentals. Every engagement.

These do not depend on an agent brand, model or IDE.

  1. Spec before build

    Agree scope, acceptance criteria, failure cases and non-functional requirements before implementation. The agent needs a definition of success it can check, not just a request to "make it work".

  2. Engineer the context

    Put client rules, naming standards, glossary, architecture decisions and definition of done in the repo. Keep them concise and current. Reference the right skill instead of repeating a long prompt.

  3. Bound the autonomy

    Use approved DEV environments, branches and least-privilege identities. Limit tools and require approvals for risky actions. The agent does not get TEST or PROD credentials or permission to approve its own release.

  4. Review every change

    Every change goes through a PR, including configuration and skills. Review intent, source diffs, dependencies and evidence. The agent can help review; a person remains accountable for the merge.

  5. Show verification evidence

    Map each criterion to a result. Include applicable tests, solution checker results, role-based checks and known limitations. "The agent says it works" is not evidence.

  6. Close the feedback loop

    Retrospectives turn recurring rework into better rules, examples or skills. Review updates through a PR, then rerun the affected checks. Do not let personal agent memory become the team's only knowledge.

Guidance is not enforcement.

Instructions influence behavior; identity, environment access and tool permissions constrain it. A deny rule for one command cannot stop equivalent API or MCP operations. A branch does not isolate changes to a live DEV environment.

From idea to production

Seven stages, each with a human owner and an explicit sign-off. Return to an earlier stage when scope, risk or assumptions change.

The agent helps the backlog. It does not own it.

Draft candidates

Use approved workshop notes to suggest stories. A person keeps, rewrites or discards them.

Refine a story

Clarify criteria, suggest smaller slices and add edge cases without changing agreed scope.

Review for gaps

Flag duplicates, dependencies, missing non-functionals and conflicts with the design.

The product owner decides what enters the backlog, its priority and when it is accepted. The agent must not add, reorder or mark items done without permission.

Administrator checklist: Dataverse MCP
  1. Get the approved DEV environment and the administrator who owns this change.
  2. In Power Platform admin center: Manage > Environments > select DEV > Settings > Product > Features.
  3. Check "Allow MCP clients to interact with Dataverse MCP server", then open Advanced Settings.
  4. For Claude Code, enable its required registered client record: Is Enabled = Yes, then Save & Close.
  5. For GitHub Copilot CLI, enable its required registered client record separately.
  6. For Copilot in VS Code, check and enable the record actually used by that authentication route. Do not assume every UI surface has a distinct record, or that enabling Claude enables Copilot.
  7. Record client names/IDs and test each selected route with a least-privilege DEV identity. Missing records or denied consent go back to the administrator, not a workaround.

Allowlisting applies to the /api/mcp entrypoint, not all Dataverse APIs. Identity and environment restrictions still apply. Microsoft administration reference.

Before any client work

These checks belong to the engagement, not just the developer's machine.

  • Approval and data

    Record permitted AI products, models, connectors and data classes. Confirm the client's AI policy, retention, residency, contractual requirements and Microsoft 365 data approval. Use synthetic data unless approved otherwise.

  • Identity and boundaries

    Use a DEV-only, least-privilege identity. Inspect PAC, Azure CLI, MCP OAuth, browser sessions, environment variables and cached credentials. Do not elevate the agent to bypass a failed operation.

  • Untrusted content

    Treat prompts in retrieved documents, tool outputs and dependencies as data, not authority. Review plugins and MCP server publishers, pin approved versions where supported and inspect updates.

  • Cost and licensing

    Confirm developer subscriptions, platform licences and tenant consumption. Set budgets, alerts and caps where supported. Separate subscription allocation from per-story usage cost.

  • Reviewable source

    Export or synchronize low-code changes into source and review the diff before promotion. Store solution-owned assets in solutions; review application code and infrastructure in their own source folders.

  • Release and operation

    People approve TEST and PROD promotion through the agreed ALM route. Record rollback, support ownership and monitoring. Never give an agent permission to self-approve, merge or promote its own change.

Sprint rhythm: refinement checks readiness; planning agrees scope and budgets; daily reviews inspect blockers and evidence; demos use realistic roles; retros update the shared rules and skills. Stop and escalate an access breach, unapproved data use or unexplained destructive change.

Choose with evidence, not allegiance

The playbook is the test harness for tool choice. There is no declared winner in this first version.

Three real stories

  1. A Dataverse table set: relationships, publisher prefix, solution membership and role-based access.
  2. A cloud flow: connection references, environment variables and a deliberate failure path.
  3. A Copilot Studio topic: representative phrases, permissions and evaluation evidence.

Run each story in both tools with the same approved spec, rules, skills and starting artifacts. Use the same developer; alternate tool order to reduce learning bias.

Measure the accepted result

  • Review defects, severity and rework time
  • Standards and DEV-only compliance
  • Elapsed time, hands-on time and interventions
  • Usage cost and allocated subscription cost
  • Setup friction and developer preference

Record model, tool/plugin versions and the Copilot surface. Use isolated DEV state and a consistent reviewer. A serious boundary breach fails the gate; lower cost does not offset it.

Three stories offer directional evidence, not a universal ranking. Decide by workload, constraints and client policy. Keep the fundamentals unchanged whichever adapter you select. Read the pilot procedure.

Keep the adapters current.

After a host, plugin, MCP or policy change, review the relevant adapter, rerun its DEV setup checks and record versions and evidence. Repeated issues become reviewed improvements to the shared assets. Maintenance and publication ownership.
